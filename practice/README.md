# practice — targets that produce a deliberately nasty core dump

These are **practice targets**, not product code. They exist to produce a real coredump that exercises
every awkward case the viewer has to survive, so that the viewer is built against reality instead of
against hand-written fake data.

They are **Linux-only** (`pthread` + `dlopen`); they cannot be built on Windows.

## One command

On a Linux box, from the repository root:

```bash
bash practice/collect.sh
```

It builds, runs the targets until they crash, then bundles into `practice/out/`:

```text
practice/out/
├── crash_target.<time>.<pid>.<sig>.core   the core
├── crash_target                            the executable (with symbols)
├── libplugin.so                            the dlopen'ed object
├── smash_ra.<time>.<pid>.<sig>.core        corrupted-stack sample: return address overwritten
├── smash_fp.<time>.<pid>.<sig>.core        corrupted-stack sample: frame pointer overwritten
├── smash_data.<time>.<pid>.<sig>.core      corrupted-stack sample: a local pointer overwritten
├── smash_ra · smash_fp · smash_data        the three sample executables
├── opt_target.<time>.<pid>.<sig>.core      optimised sample: variables in registers
├── opt_target                              its executable (-O2)
├── snap_target.<time>.<pid>.<sig>.core     register-snapshot sample: a jmp_buf, and a fault inside a handler
├── snap_target                             its executable (-O2)
├── sysroot/…                               every shared library the programs used
└── manifest.txt                            generated by collect.sh: the build, the cores, the crash frames
```

Copy the whole bundle to whichever machine will analyse it — that machine needs the cores **and** the
binaries, or it will only see addresses:

```bash
scp -r practice/out you@your-analysis-host:/tmp/practice
```

## What the target deliberately contains

| In the target | Which viewer behaviour it forces |
|---|---|
| 3 extra threads: one holding a mutex, one blocked on that mutex, one working | the thread list is not a flat list of identical things; thread states differ |
| a linked structure `head → b → c → head` (**a cycle**) | cycle detection: following `next` must not run forever |
| a `NULL` pointer field | must render as `NULL` and be **not clickable** |
| a **stray pointer** (`0xdead0000dead0000`) that is dereferenced | "this address is not in the dump" — a normal result, not a crash |
| a 24-frame recursion below `main` | the stack tree has real depth |
| a frame with **thirteen arguments** of mixed types (`stacked_args`: pointers, a string, `NULL`, a struct **by value**, a `double`, a `uint64_t`) — more than the ABI's eight argument registers, so some of them live **on the stack** | a frame card has to stay readable when the argument list is longer than a line; the merge (`×24`) and the unfold exist for the same reason |
| a frame **inside `libplugin.so`** at the crash site | `NT_FILE` mapping: the memory view must name the object a range belongs to |
| heap allocations that are never freed | the memory view has heap regions with real content |
| the whole thing compiled `-g -O0` | symbols present — and `STRIP=1 practice/collect.sh` gives the opposite case |

`manifest.txt` in the bundle is **generated by `collect.sh`**, not written by hand: it records the build, the
cores this run produced, and the crashed thread's top frames read back out of the core with gdb. Anything a
reader could measure from the bundle belongs there, so that it cannot go stale in silence — the tables above
are the prose that says *why* each case is in the target.

## The corrupted-stack samples

A stack is untrusted input, and a viewer that has only ever seen intact stacks has untested corruption
handling. A core cannot be edited after the fact to make one — gdb answers memory *and* register writes on
a core with *"You can't do that without a process to debug"* — so the corruption has to be manufactured.
`src/smash_target.c` is that: it writes into its own frame record through `__builtin_frame_address(0)`
rather than overflowing a buffer into position, because a sample that depends on where the compiler put a
16-byte array is a coincidence, not a fixture.

| Sample | What is corrupted | What it leaves behind (measured) |
|---|---|---|
| `smash_ra` | both words of the frame record, so `ret` jumps to `0x4141414141414141` | SIGBUS on the misaligned PC; gdb reports **two `??` frames** with that address as the pc, and says nothing else — no "corrupt stack" message at all |
| `smash_fp` | only the frame pointer | the crash is a clean SIGSEGV in symbolised code; DWARF CFI still unwinds `crash_here → main`, while the frame pointer chain above it is a lie |
| `smash_data` | a local pointer, control flow untouched | a SIGSEGV whose faulting address is the marker, with a **verifiably intact** stack under it |

Built with `-fno-omit-frame-pointer` (a frame chain is a given here, not a compiler default) and
`-fno-stack-protector` (a deliberate write into a frame record must not be turned into an abort by the
canary check — these samples are about what a *silent* overflow leaves behind).

## The optimised sample

`opt_target` is the same idea for a different gap: at `-O0` every variable is spilled to the stack, so a
viewer can pretend a frame is a list of memory slots. A release build does the opposite — arguments and
locals live in **registers**, and a variable has no address at all. Built `-O2 -g -fno-omit-frame-pointer`:

| What it shows | Measured |
|---|---|
| the crash frame's argument `target` | no address; `info address` says `a variable in $x19` — and *which* register is a function of the pc, so gdb answers with one location per range |
| the **same** frame's `main` | a `volatile` local (`pinned`) which cannot live in a register, so it has a real stack slot |
| `total`, also in `main` | multi-location, and at the faulting pc its location is the very slot `pinned` was written into: two names, one slot |

## The register-snapshot sample

Every other target saves only what a small function needs — the frame pointer and the return address — so in an
outer frame `info registers` has almost nothing real to restore and gdb falls back to *"assume the same as the
inner frame"*. That is an assumption, and a viewer that repeats it as fact is inventing values.

`snap_target` puts whole register files on the stack, two ways at once: a `jmp_buf` declared as a **local** (so
`setjmp` writes it into `main`'s frame, not `.bss`), and a SIGSEGV handler that faults again, so the kernel's
`sigcontext` is still there and gdb shows its `<signal handler called>` frame. Built `-O2`, because at `-O0`
nothing is ever kept in a callee-saved register for it to save.

| | ordinary target | snapshot target |
|---|---|---|
| registers differing across frames | **4** (`pc`, `sp`, `x29`, `x30`) | **6** (the same four, plus `x0` and `x1`) |
| where the extra two come from | — | the handler's own fault address (`x0 = 0x4141414141414141`) and the state under it |

The honest limit of that table: "differs across frames" **under-counts** what a frame can restore. `x19`–`x21`
and the vector registers are saved here too, and report identical values simply because they hold the same value
throughout this run. Telling *recoverable* from *assumed* needs more than `info registers` — which is why a
viewer has to mark that distinction itself rather than inherit it.

**Keep target names to 15 characters or fewer.** A core file is named after the process's `comm`, and the
kernel caps that at 15: `optimized_target` produced `optimized_targe.<time>.<pid>.<sig>.core`, which every
tool that looks a core up by program name then failed to find — silently. `opt_target` is named for that
reason, and `collect.sh` warns when a target produces no core instead of shipping a bundle without it.

## The heavy sample: scale instead of awkwardness

Everything above is *awkward*. `heavy_target` is the one that is **big**, because size is a claim the viewer
makes — "cores are GB-scale and a stack can have tens of thousands of frames" (`docs/requirements.md` §5) — and
a core the size of a small machine's memory is the only thing that can test it. It is opt-in, since its cost is
the point:

```bash
HEAVY=1 bash practice/collect.sh                                  # 48 threads, 30 000 frames, 1 GB of heap
HEAVY=1 HEAVY_DEPTH=60000 HEAVY_HEAP_MB=2048 bash practice/collect.sh
```

| in the target | measured on the practice core |
|---|---|
| 48 threads in four states (one holds a mutex, the rest block on it, some sleep, some work) | 48 threads in the dump, and the crash frame's own thread is at the **bottom** of the stack |
| 30 000 frames of recursion, each writing a 64-byte buffer | the crashed thread reports **30 002 frames** |
| 1 GB of touched, live heap (never freed) | the core is **1.13 GB**, and the largest mapping is **1.07 GB** |
| a crash at the bottom, dereferencing `0xdead0000dead0000` | the same recognisable "not in this dump" answer the other targets produce |

**Two numbers here are surprising, and both are about the kernel rather than about us.** An anonymous mapping
is written to the core **in full**, whether or not its pages were ever touched — so the 48 helper threads ask
for a 1 MB stack each rather than a comfortable 32 MB, because 48 × 32 MB would have put 1.5 GB of zeroes into
the dump and drowned the heap this sample is about. The same rule is why `crash_target`'s own core grows from
25 MB to 50 MB when the collector raises `ulimit -s` for this scenario: the main thread's stack is a mapping
too, and it is dumped whole.

The depth is real rather than nominal for the same reason: the recursion is built `-O0` with frame pointers, so
30 000 calls are 30 000 frames, and the fault is at the deepest one. That is what makes a *window* of the stack
the interesting question — asking for twenty frames at offset 20 000 is a different problem from asking for the
first twenty, and it is the problem this sample exists to pose.

## Extending it

Add a new scenario as `practice/src/<name>.c` plus a branch in `collect.sh`, and keep every scenario
**reproducible**: one command, same core, every time. A core you cannot reproduce is a core you cannot
debug twice.
